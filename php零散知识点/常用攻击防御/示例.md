##  场景: 官网攻击者不停随机切换参数,ip,打满php-fpm

公开匿名例如门店接口防御（无需登录、不能弹窗验证码、不能强制登录）

现状复盘：

- 完全公开接口，**所有访问都是匿名，不能登录、不能弹验证码破坏普通用户体验**
- 攻击者代理池，IP 每请求都变，裸 HTTP 脚本，疯狂遍历随机查询参数组合
- 伤害来源不是 QPS 高，是**海量不同查询条件，生成大量不同 SQL，打满 MySQL CPU**
- 不能把真实访客拦死，官网普通游客可以正常查门店

> 核心结论：**这种场景做不到 100% 拦截请求，但可以做到：就算请求源源不断进来，数据库不会崩，网站不会卡死。** 不要追求识别坏人，重点：**限制查询的破坏力 + 全局接口降级 + 约束 SQL 代价**。

**关键现实约束**

1. ❌ 不能强制登录
2. ❌ 不能随便弹人机验证 / 图片验证码（普通游客访问会中招，体验灾难）
3. ❌ IP 限流基本报废
4. ❌ Session/token 做身份不可靠，攻击者可以随便带 Cookie
5. ✅ 允许正常游客多条件筛选
6. ✅ 攻击来的时候，优先保证网站整体可用，可以**适度阉割门店列表接口能力，不能让整个官网挂**

### 整套落地方案，按优先级排序

### 1、参数层硬约束（第一道闸门，必做，修改量最小）

攻击者疯狂拼接十几个查询参数，**直接限制查询的复杂度，从源头降低 SQL 压力**

1. **查询字段白名单**，不在白名单直接丢弃，绝不拼接 SQL where。
2. **限制有效过滤条件最大数量：最多允许 2 个有效筛选条件**

> 真实游客：城市 + 区域 / 城市 + 品牌，最多 2 个条件足够用。 攻击者喜欢同时塞 5‑8 个随机条件组合出海量 SQL。
>
> > 逻辑：统计本次 GET 里面真正生效的过滤条件数量，超过 2 个直接丢弃后面多余条件。

1. **禁止无任何筛选条件查询全表**

> 如果没有任何有效筛选条件，强制默认带上一个全局范围限制（例如限制省份，或者直接返回热门门店固定缓存数据，禁止全表扫描）

1. 分页强限制
   - page_size 最大 50，大于 50 强制改写为 50
   - page 最大上限，例如最大 500 页，超过直接返回空数组，防止无限翻页扫描
2. 所有 ID 参数强制校验为正整数；枚举值校验；空字符串直接丢弃该条件，不要进 SQL。

> 这一步做完，攻击者就算发一万次请求，每条 SQL 都很简单，索引命中，不会生成大量奇怪的执行计划。



### 2、MySQL 侧兜底，防止单条慢查询杀死数据库（保命配置）

1. `max_execution_time=1500` 单位毫秒，select 超过 1.5 秒直接 kill 这条 SQL，不会占数据库线程。
2. 建立合理联合索引，不要建几十条索引。优先高频筛选字段。
3. **所有查询强制 LIMIT**，代码层面写死，不依赖前端参数。
4. 关闭 MySQL 慢查询日志告警以外，监控门店相关 SQL 的执行时间。

> 就算前面业务逻辑漏网，数据库本身有熔断，不会一条 SQL 拖垮整个实例。

### 3、Redis 做两个全局监控（无 IP、无用户身份，接口全局维度）

> 不针对某个人，监控**整个门店接口的全局状态**，Redis 存，伪代码逻辑： 指标 A：`store:api:total_qps` → 滑动窗口统计 60 秒接口总请求数 指标 B：`store:api:sig_set` → 滑动窗口 60 秒内，收集**有效查询参数 hash 签名集合**，统计有多少种不同参数组合。

触发降级保护模式条件（满足任意一个就开启保护）

1. 60 秒总请求 > N（根据你的业务，例如 > 200）
2. 60 秒内出现**超过 120 种不同的参数签名组合**（这个对你场景最有效，攻击者疯狂随机参数会瞬间打爆这个数字，真实用户几乎不可能）

> 👉 真实用户几十个人同时访问，参数组合数很少；攻击者随机十几个字段，一秒就能生成几十上百种不同参数 hash。

#### 【降级保护模式开启后】重点！不能返回 429，不能拦截用户，而是阉割查询能力

> 千万不要直接 429，会误伤普通游客！ 降级模式生效期间（持续 90 秒，时间到自动恢复）：

1. **只允许最多 1 个筛选条件，多余全部丢弃**，一般只允许 city_id
2. area_id、brand_id 等其他筛选参数全部忽略
3. page_size 强制固定 20，禁止自定义
4. **强制走 Redis 缓存，哪怕缓存 TTL 很短，尽量不穿透 MySQL**
5. 模糊搜索直接禁用

效果：

- 普通游客：还可以选城市看门店，只是不能多条件筛选；网站整体正常。
- 攻击者：无论传多少乱七八糟的查询参数，全部被抹平，只能执行简单单条件查询，大量请求命中缓存，MySQL 压力暴跌。
- 90 秒后流量平息，自动恢复完整多条件查询能力。

> 这个是你这种**公开匿名接口最核心的防御手段**。不识别攻击者是谁，发现扫描行为，主动降低接口能力保数据库。

### 4、缓存策略，注意坑点

用参数 hash 做 Redis 缓存 key，TTL 60‑120 秒。 ⚠️ 但是攻击者会生成大量独一无二参数，大量缓存 miss，**缓存不能作为主力防御，只能做辅助**。 不要设置过大 TTL，门店有更新需要清理对应缓存。

### 5、WAF 怎么配置（公开匿名接口，不能乱弹验证）

1. **关闭单 IP CC 防护，完全没用**。
2. 不要全局开启 JS 挑战，因为公开接口，部分爬虫、小程序、部分客户端访问会直接挂掉。
3. WAF 做**告警**：监控 `/api/store/list` URI 的 QPS，到达阈值给运维告警，让你知道正在遭受攻击。
4. 如果云 WAF 支持：配置**请求特征规则**，对高频变化 query 参数的访问做标记，仅做日志，不要直接拦截。

> 公开匿名官网接口，WAF 能做的有限，主要靠业务层降级兜底。

### 6、架构备选：把门店查询移出 MySQL（终极方案）

如果条件允许： 门店基础数据同步到 Elasticsearch，门店列表全部查询 ES。

- ES 天生擅长海量多条件随机过滤；压力消耗在 ES，不会搞垮业务 MySQL。
- MySQL 只用来做业务写入。

> 没有 ES 折中方案：预计算多维度 Redis 集合，但是开发成本高。

## ❌ 这些方案直接放弃，不要浪费时间

1. ❌ IP 限流、IP 黑名单：代理池无限换 IP，无效。
2. ❌ Cookie/Token/session 限流：匿名接口攻击者可以随便伪造，无法信任。
3. ❌ 设备 / 浏览器指纹：脚本可以全部伪造。
4. ❌ 验证码、人机验证弹窗：公开官网接口，严重伤害正常游客体验。
5. ❌ 指望缓存扛全部攻击：攻击者随机参数会大量穿透缓存。

## 整体防御链路（完整跑通）

1. WAF：告警，不随便拦截；
2. 进入业务代码：参数白名单，限制最多 2 个筛选条件，分页上限，禁止无条件全表查询；
3. Redis 全局统计：接口总请求数 + 参数组合签名数量；
4. 一旦触发扫描阈值 → **自动开启降级保护模式 90 秒，阉割多条件查询能力**；
5. 查询优先走 Redis 缓存；
6. MySQL 层：语句超时熔断，强制 LIMIT，合理索引兜底。

> 核心思想： 公开匿名接口，**你拦不住请求流量，但你可以控制每一个请求对数据库造成的伤害。攻击来了，牺牲门店接口部分筛选功能，保住整个官网和数据库不死。**

## PHP7 极简伪代码示例（核心逻辑）

```php
<?php
// 门店公开接口，无需登录
$allowFilter = ['city_id','area_id','brand_id','status'];
$input = $_GET;

//1.参数白名单过滤
$rawParams = [];
foreach($input as $k=>$v){
    if(in_array($k,$allowFilter)){
        //简单类型校验
        if($k == 'city_id' || $k == 'area_id' || $k == 'brand_id'){
            $v = (int)$v;
            if($v <=0) continue;
        }
        $rawParams[$k] = $v;
    }
}

//2.读取redis降级标记
$isDegrade = $redis->get("store:api:degrade_switch");
$maxFilter = $isDegrade ? 1 : 2;

//截取最多允许的筛选条件
$validParams = array_slice($rawParams,0,$maxFilter);

//禁止无筛选条件
if(empty($validParams)){
    //这里返回默认城市缓存数据，禁止全表查询
    return getDefaultStoreCache();
}

//分页处理
$pageSize = min((int)($_GET['size']??20),50);

//计算本次参数签名，用于全局统计
$paramSig = md5(http_build_query($validParams));

// 把签名加入redis集合，统计60秒内不同参数组合
$redis->sAdd("store:api:sig_set",$paramSig);
$redis->expire("store:api:sig_set",60);
$diffCount = $redis->sCard("store:api:sig_set");

//判断是否触发降级
if($diffCount > 120 && !$isDegrade){
    //开启降级保护90秒
    $redis->setex("store:api:degrade_switch",90,1);
}

//查询逻辑优先读取缓存，再查Mysql，Mysql强制LIMIT
//mysql max_execution_time=1500
```
