##  场景: 官网攻击者不停随机切换参数,ip,打满php-fpm

公开匿名例如门店接口防御（无需登录、不能弹窗验证码、不能强制登录）

现状复盘：

- 完全公开接口，**所有访问都是匿名，不能登录、不能弹验证码破坏普通用户体验**
- 攻击者代理池，IP 每请求都变，裸 HTTP 脚本，疯狂遍历随机查询参数组合
- 伤害来源不是 QPS 高，是**海量不同查询条件，生成大量不同 SQL，打满 MySQL CPU**
- 不能把真实访客拦死，官网普通游客可以正常查门店

> 核心结论：**这种场景做不到 100% 拦截请求，但可以做到：就算请求源源不断进来，数据库不会崩，网站不会卡死。** 不要追求识别坏人，重点：**限制查询的破坏力 + 全局接口降级 + 约束 SQL 代价**。

**关键现实约束**

1. ❌ 不能强制登录-
2. ❌ 不能随便弹人机验证 / 图片验证码（普通游客访问会中招，体验灾难）
3. ❌ IP 限流基本报废
4. ❌ Session/token 做身份不可靠，攻击者可以随便带 Cookie
5. ✅ 允许正常游客多条件筛选
6. ✅ 攻击来的时候，优先保证网站整体可用，可以**适度阉割门店列表接口能力，不能让整个官网挂**

```php
1. 公开匿名接口，不能登录、不能弹验证码
2. 门店列表：MySQL，多张表 JOIN，不能迁移 ES
3. 正常用户允许 4‑5 个筛选条件，不能偷偷删条件、不能篡改查询条件
4. 攻击者代理池，IP 不断切换，疯狂随机组合各个查询参数，生成大量不同 SQL 打 CPU
5. 不能简单粗暴限制条件数量，业务需要复杂筛选
6. 攻击目标：制造大量不同执行计划，命中差索引、临时表、filesort，把 MySQL CPU 打满
```

现实矛盾：

> 真实正常用户：就是需要同时选城市、区域、品牌、业态，4 个条件组合筛选，业务上合理，不能直接丢掉。 攻击者：疯狂随机排列组合十几个字段，生成成千上万种 SQL，打 CPU。

所以不能一刀切：**不能把用户的条件强行删掉，而是要区分：什么情况下允许复杂多条件，什么情况下限制复杂查询。**

**也不能走es**

门店列表不是单表，是**7‑8 张表 JOIN 出来的结果**，有门店主表、区域、品牌、标签、业务类型、营业时间、扩展属性……

- ES 适合**宽表扁平化数据**；多表复杂 JOIN 要做数据同步 + 宽表重构，开发、维护、同步一致性成本很高，改动一张关联表就要重新刷宽表。业务频繁变更的情况下，ES 确实不现实，直接放弃 ES 这条路。
