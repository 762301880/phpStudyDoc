## 核心

HTTP 主打「跨语言、通用、浏览器可直接调用」；

RPC 主打「服务之间内部通信，追求高性能、强契约、便捷开发」。两者定位不一样，不是谁替代谁。

> 常见架构分工：
>
> 前端 ↔ 后端网关 / 应用服务：**HTTP/HTTPS（REST）**
>
> 后端各个微服务之间互相调用：**RPC**

## 两者本质

### HTTP

HTTP 是**应用层通用协议**，基于 TCP，设计初衷是浏览器和服务器通信。

- 文本为主（JSON/Form）；
- 标准规范全世界通用；
- 端口默认 80/443，防火墙友好。

### RPC（远程过程调用）

RPC **不是单一协议**，是一套思想：像调用本地函数一样调用远程机器上的方法。

流行实现：gRPC、Dubbo、Thrift、brpc。

很多 RPC 底层依然跑 TCP（也可以基于 HTTP2，例如 gRPC）。

## 为什么服务内部通信偏爱 RPC

### ① 序列化性能差距巨大

HTTP 常用：**JSON**

- 文本格式，体积大、解析慢、需要字符串转数字；
- 传输大量数据时开销很高。

RPC 一般用：**Protobuf / Hessian / Thrift（二进制序列化）**

- 二进制编码，压缩后体积远小于 JSON；
- 编解码速度更快，CPU 消耗更低；

> 微服务大量互相调用，高频场景下差距会被持续放大。

### ② 天然「方法调用」语义，REST 做不到

REST HTTP：

```http
POST /user/getUserInfo
{ "userId": 1001 }
```

只是约定的接口规范，**没有强制契约**。参数写错、字段类型不对，运行时才报错。

RPC：直接定义服务 + 方法

```php
service UserService {
  rpc GetUserInfo(GetUserReq) returns (UserResp);
}
message GetUserReq {
  int64 userId = 1;
}
```

1. IDL 文件定义契约；

2. 自动生成客户端、服务端代码；

3. **编译期就能校验参数类型**；

​    调用形式像本地函数：`userService.GetUserInfo(1001)`

​     不用手动拼 URL、组装 JSON、处理 http header。

### ③ 更完善的内置治理能力（微服务刚需）

Dubbo、gRPC 原生支持：

- 服务注册发现（Nacos/ZooKeeper）
- 负载均衡、权重路由、灰度发布
- 超时重试、熔断、限流
- 连接复用、长连接池

原生 HTTP（SpringMVC REST）想要这些能力：

你需要自己封装 HTTP 客户端、自己实现负载均衡、连接池、重试，大量重复造轮子。

> RPC 框架**生来就是为分布式服务调用设计**，HTTP 只是通用传输协议。

### ④ 连接模型优势

普通 HTTP/1.1：短连接居多，频繁建立断开 TCP，有握手开销；

RPC 普遍使用**长连接 + 连接池**，一次建立长久复用，高并发下延迟更低。

> gRPC 基于 HTTP/2，同样长连接、多路复用，所以 gRPC 也是 RPC。

## HTTP 不能被 RPC 取代的场景

千万别觉得 RPC 更强就全部改用 RPC：

1. **前端浏览器无法直接调用原生 TCP-RPC**（浏览器只有 HTTP/WS）；
2. 对外开放 API、第三方对接：必须 HTTP，通用性第一；
3. 简单低并发项目，不想引入复杂框架，REST HTTP 足够简单、调试方便（Postman、curl 随手测）。

## 直观对比表

| 维度         | HTTP REST               | RPC(gRPC/Dubbo)               |
| ------------ | ----------------------- | ----------------------------- |
| 适用场景     | 前端↔后端、对外开放接口 | 后端微服务内部互通            |
| 数据格式     | JSON（文本）            | Protobuf/Hessian（二进制）    |
| 调用方式     | 拼 URL、组装请求体      | 像调用本地函数                |
| 契约         | 无强制约束，靠文档      | IDL 定义，代码自动生成        |
| 性能         | 一般，序列化开销大      | 更高，体积小、速度快          |
| 调试工具     | curl、Postman，极其方便 | 需要专用工具，调试麻烦        |
| 跨网络防火墙 | 80/443 基本放行         | 自定义 TCP 端口，外网容易拦截 |

## 主流架构最佳实践（行业标准）

```php
【浏览器/APP】 → HTTP/HTTPS → 【API网关】
                                 ↓ RPC
                        ┌───── 用户服务
                        ├───── 订单服务
                        └───── 支付服务
```

外网入口：统一 HTTP

网关往后，服务之间内网通信：RPC 提升吞吐量、降低延迟



## 极简总结

**对外、给人 / 浏览器调用：用 HTTP REST，通用好调试**

**内网服务之间互相疯狂调用：用 RPC，更快、开发更规范、自带微服务能力**

---

## RPC是不是只能在同一个内网中调用 例如 A 服务器的 AB 项目

**RPC ≠ 只能内网调用，RPC 完全可以跨公网访问，只是绝大多数业务「选择只在内网用 RPC」，不是技术限制。**

**RPC 没有强制内网限制，是安全、运维、业务成本的考量，让大家只在内网使用 RPC；对外互通首选 HTTP，通过网关中转 RPC。**

> A 服务器上 AB 两个项目、或者多台内网服务器之间互相调用 → 非常适合 RPC（标准用法）
>
> 如果强行把 RPC 端口放公网让外网机器调用 **技术可行，但架构不规范、不安全，生产不推荐**
