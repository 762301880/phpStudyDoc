## 一,cdn 是什么 网站为什么需要cdn

### CDN 的定义

CDN 的全称是 Content Delivery Network，中文叫做**内容分发网络**，是一种在互联网中部署的分布式的网络服务架构，核心是在不同的地理位置，部署很多的缓存服务器（也叫边缘节点）。

简单类比的话：可以把 CDN 理解成是电商的全国仓库网络，电商会把热门的商品，提前放在离各个买家更近的仓库里，用户下单之后，直接从最近的仓库发货，而不是全部从总仓库调货。CDN 的边缘节点就相当于这些本地仓库，网站的静态内容（比如图片、视频、JS/CSS 文件）就是这些热门商品。

### 网站需要 CDN 的核心原因

1. 提升网站访问速度

   普通的网站，所有的内容都存储在源服务器上，如果用户和源服务器的地理位置很远，数据传输的路径会很长，经过的网络节点很多，延迟会很高，打开网站的速度就会很慢；而 CDN 会把网站的静态内容，缓存到离用户最近的边缘节点上，用户访问的时候，直接从边缘节点获取内容，传输距离大大缩短，加载速度会有明显提升。

2. 缓解源服务器的压力

   如果网站的访问量很高，所有的请求都直接访问源服务器，源服务器的带宽、计算资源会被快速消耗，甚至会出现服务器崩溃、网站无法访问的情况；CDN 会承接大部分的静态内容请求，源服务器只需要处理动态内容的请求（比如用户的登录、提交表单），可以极大降低源服务器的负载。

3. 提升网站的稳定性和可用性

   当源服务器出现故障、或者某个地区的网络出现问题时，CDN 的边缘节点可以继续提供缓存的内容，用户依然可以正常访问网站的静态部分；同时 CDN 一般都有负载均衡和故障自动切换的机制，能避免单点故障的影响。

4. 防御网络攻击

   很多 CDN 服务商都提供基础的安全防护能力，比如可以抵御 DDoS 攻击（流量型攻击），CDN 会把恶意的流量在边缘节点就进行拦截，不会传递到源服务器，保护源服务器的安全。

### 模拟对比的方式，来帮你感受使用 CDN 和不使用 CDN 的区别

> 就模拟一个用户访问网站的全过程：

#### 模拟场景：一个位于上海的用户，访问一台部署在深圳的网站

1. **没有使用 CDN 的情况**
   1. 用户在浏览器输入网址，发送访问请求
   2. 请求先从用户的电脑，传到上海的运营商节点，之后依次经过江苏、浙江、广东的多个网络中转节点，最终到达深圳的源服务器
   3. 源服务器接收到请求之后，开始处理，把需要返回的图片、网页文件，再沿着刚才的路径，反向传回给用户
   4. 整个过程中，数据传输的路径大概有 1300 公里左右，加上每一个中转节点都需要处理数据，大概需要花费**300ms-800ms 甚至更久**的时间，你会看到浏览器的加载图标一直在转，网页的图片、内容是一点点跳出来的，要是遇到访问高峰，源服务器压力大，可能还会加载失败。
2. **使用了 CDN 的情况**
   1. 用户在浏览器输入网址，发送访问请求
   2. 请求只会传到上海本地的 CDN 边缘节点（这个节点可能就在用户所在的行政区，距离只有几十公里）
   3. 这个边缘节点上已经缓存了这个网站的图片、网页文件，直接就把内容返回给用户
   4. 整个过程数据传输的路径极短，中转节点很少，只需要花费**50ms-150ms**的时间，你打开网页的时候，几乎是瞬间就看到完整的内容，就算是访问高峰，也不会有明显的加载延迟

### 模拟**DDoS 攻击时，CDN 的防护效果对比**

模拟场景：网站遭遇针对源服务器的流量型 DDoS 攻击，攻击流量是 100Gbps

1. **没有使用 CDN 的情况**
   1. 攻击者发起的 100Gbps 的恶意流量，会直接沿着网络路径，全部冲向深圳的源服务器
   2. 普通的网站源服务器，带宽一般只有 10Gbps-50Gbps，这个攻击流量远远超过了源服务器的承载上限
   3. 源服务器的带宽会在几秒钟内被占满，不仅无法处理正常用户的访问请求，严重的话还会直接被运营商暂时封禁 IP，或者服务器硬件直接因为过载损坏
   4. 此时不管是上海的用户，还是其他地区的用户，都会直接无法打开这个网站，一直显示加载失败
2. **使用了 CDN 的情况**
   1. 攻击者发起的 100Gbps 的恶意流量，首先会冲向 CDN 的边缘节点网络
   2. CDN 的边缘节点集群整体的带宽承载能力非常高，一般可以达到 Tbps 级别（1Tbps=1024Gbps），100Gbps 的攻击流量只会占用一小部分的带宽资源
   3. 同时 CDN 的防护系统会识别出这些恶意流量，在边缘节点就直接进行拦截、清洗，不会把这些流量传递到深圳的源服务器
   4. 上海的用户，以及其他地区的正常用户，依然可以从 CDN 的边缘节点获取缓存的内容，正常访问网站，不会受到攻击的影响

### **CDN 的实际部署的简单步骤**

CDN 的实际部署，针对普通的中小网站来说，步骤是比较简单的，一般分为这几步：

1. 选择 CDN 服务商并完成注册

   先挑选合适的 CDN 服务商，国内常见的有阿里云 CDN、腾讯云 CDN、百度云加速等，完成服务商平台的账号注册和实名认证。

2. 添加需要加速的网站域名

   在 CDN 服务商的管理后台，找到 CDN 加速的入口，添加自己的网站域名，同时需要选择这个域名的业务类型，比如是静态网站、动态网站、视频网站，方便 CDN 进行针对性的配置。

3. 配置源服务器信息

   填写网站源服务器的 IP 地址或者源域名，CDN 会把这个源服务器的内容同步到边缘节点；同时可以配置缓存规则，比如指定哪些文件需要缓存、缓存的时长是多久。

4. 修改域名 DNS 解析

   这是关键的一步，需要到你的域名注册商的后台，把域名的 DNS 解析记录，从原来指向源服务器的记录，修改为指向 CDN 服务商提供的 CNAME 地址，这样用户的访问请求才会先进入 CDN 网络。

5. 验证配置并上线

   修改解析之后，等待 10 分钟 - 60 分钟的 DNS 生效时间，之后可以在 CDN 后台验证加速是否生效，也可以用浏览器访问网站，测试访问速度，确认没问题之后，CDN 就正式开始为网站提供服务了

## 二，Http与Https的区别

**HTTP**：超文本传输协议，明文传输，端口 **80** 

**HTTPS**：HTTP + SSL/TLS 加密，密文传输，端口 **443**

###  核心对比

| 对比项     | HTTP                                 | HTTPS                                             |
| ---------- | ------------------------------------ | ------------------------------------------------- |
| 传输方式   | **明文传输**                         | SSL/TLS 加密密文传输                              |
| 默认端口   | 80                                   | 443                                               |
| 安全性     | 数据裸奔，中间人可以窃听、篡改、劫持 | 加密传输，防窃听、防篡改、防劫持                  |
| 证书       | 不需要 SSL 证书                      | 需要 CA 颁发 SSL 证书，有成本                     |
| 性能       | 开销小，速度快                       | 加密解密会有少量性能损耗 (现代服务器几乎感知不到) |
| 浏览器标识 | 地址栏不安全警告                     | 小锁标识，安全                                    |
| SEO        | 搜索引擎权重低                       | 搜索引擎优先收录，权重更高                        |

### 通俗理解

- **HTTP**：寄明信片，路上任何人都可以偷看、修改内容。
- **HTTPS**：把信件放进密封加密信封，只有收发双方可以拆开读取。

### HTTPS 做了两件关键事

1. **加密通信**：传输的数据乱码，中间人截获也看不懂。
2. **身份认证**：SSL 证书确认访问的网站是真实官网，防止钓鱼网站冒充。

### 实际场景

- HTTP：现在基本淘汰，很多浏览器会标记 “不安全”，表单输入会告警。
- HTTPS：现在所有正规网站、小程序、App 接口都强制 HTTPS。

### 访问跳转

现在服务器一般配置：**80 端口 HTTP 301 重定向到 443 HTTPS**，用户输入 http 自动跳转到 https。

### HTTPS 到底加密了啥？(重要理解)

> HTTP：**全部内容明文裸奔**，网络中间设备（路由器、运营商、抓包工具）可以直接看到完整数据。 HTTPS：**HTTP 报文全部加密**，但是**IP 和端口不加密**

举个现实例子

你访问 `shturl.cc/m4PkGQlYVhP`，提交账号密码：

####  HTTP（明文）

抓包能直接看到：

- 你要访问哪个域名 `shturl.`
- 访问路径 `/login`
- 请求参数：`username=admin&pwd=123456`
- 返回的网页 HTML 内容

> 中间人一眼拿到你的账号密码。

#### HTTPS（加密后）

抓包工具看到的只有：

1. ✅ 明文可见（不会加密）
   - 目标服务器 IP 地址
   - 目标端口：443
   - TLS 握手的一些协商信息
   - **域名 SNI（大部分情况明文）**：知道你访问哪个网站，但**不知道你看哪个页面**
2. 🔒 被加密的部分（抓包看到一堆乱码二进制）
   - **请求路径 `/login`**
   - **请求头：Cookie、token、请求参数**
   - **POST 提交的账号、密码、表单数据**
   - **服务器返回全部 HTML、接口返回 JSON 数据**

> 中间人只知道：你正在和 `shturl.` 网站通信。 **但是不知道：你访问哪个页面、发了什么参数、提交什么密码、服务器返回什么内容。**

### 中间人抓包到底是谁在抓？

> **我访问网站，本来是：你的电脑 ↔ 目标网站服务器**
>
>  中间人（MITM）= 第三者强行插到中间，变成：**你的电脑 ↔ 攻击者机器 ↔ 网站服务器**

中间人不是 “你自己抓自己”，是**网络路径上的第三方**在截你的流量。

#### 两个场景分清，很多人搞混

#### 场景 1：别人对你做中间人攻击（黑客 / 公共 WiFi）

路径： `你的手机` → `黑客电脑(中间人)` → `路由器/运营商` → `目标网站`

流量必须经过黑客设备，他可以拦截全部数据包科普中国。

- 如果是**HTTP**：直接读明文账号密码。
- 如果是**HTTPS**：正常情况下他拿到的全是密文，**解不开**。

> 他想解密 HTTPS，必须骗你的设备信任他伪造的证书；浏览器会弹大红警告，现实中很难成功。

**现实例子** 你连咖啡馆公共 WiFi，黑客也连同一个 WiFi，利用 ARP 欺骗把自己伪装成 WiFi 网关。 你的手机所有上网数据包，都会先发给黑客机器，再转发互联网。 你毫无感知，照常刷网页，流量已经路过别人电脑。

> 这才是 HTTPS 要防的「中间人」：**网络链路里陌生第三方**。

#### 场景 2：你自己用 Charles / Fiddler 抓包（开发者调试）

这个本质也是中间人攻击，**但是是你自愿把自己变成中间人**。 路径变成： `你的浏览器` → `Charles(本机中间人代理)` → `真实网站服务器`

为什么能解密 HTTPS？

1. 浏览器流量被手动设置代理，全部交给 Charles；
2. **你手动安装并且信任 Charles 自己生成的根证书**，告诉系统：这个证书是靠谱的；
3. Charles 一边伪造证书冒充网站跟你通信，一边正常访问真实网站；
4. 流量在 Charles 程序内部被解密成明文，所以你能看见请求参数、Cookie。

> 重点：**这是你主动授权的中间人**，浏览器不会报警，因为你手动信任证书了。

> ❗ 如果你不装 Charles 证书，哪怕流量经过 Charles，HTTPS 也只能看到乱码，解密不了。

#### 用快递比喻把两者对比

正常 HTTPS：

> 你（客户端） ↔ 顺丰（互联网） ↔ 淘宝仓库（服务器） 信件放进加密密封信封。快递员（运营商、路由器、咖啡馆黑客）只能看到收件地址，**拆不开信封看不到信里写什么**。

1）黑客中间人攻击（没拿到你的信任）

> 你 → 坏人快递员 → 顺丰 → 淘宝 坏人拿到加密信封，撕不开，只能看见寄往哪里，看不到里面内容。 坏人想拆开看信，必须伪造一把假锁给你；你一眼识别假锁拒绝签收（浏览器证书告警）。

2）Charles 抓包（你自愿）

> 你 → 你的好朋友 Charles → 顺丰 → 淘宝 你**亲手把一把备用钥匙交给 Charles（安装信任证书）**。 你把加密信封寄给 Charles；Charles 拆开读内容，再重新封装新信封发给淘宝。 返回的数据同样经过他拆开，再封好给你。 全程你知情，钥匙是你主动给的。

#### 核心回答灵魂问题

> “自己请求的网站不是只能自己抓包网络请求，自己抓自己干嘛？”

1. **黑客中间人：不是你抓自己，是路上第三者抓你的流量**，HTTPS 就是防这种人偷看。
2. **Charles 抓包：确实发生在你本机，但逻辑依然是中间人；是开发者为调试接口，主动给自己做中间人**。
3. HTTPS 防御的是：**未经你允许、没有拿到你证书信任的中间人**。

> 只要设备不信任中间人证书，哪怕数据包全部被截走，HTTPS 密文也无法解密。

## 三, TCP与UDP的区别

TCP：传输控制协议，**面向连接**；UDP：用户数据报协议，**无连接**。

### 核心对比

| 对比项          | TCP                                                          | UDP                                                      |
| --------------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| 连接特性        | 面向连接，通信前三次握手建立连接，结束四次挥手断开           | 无连接，不用建立、断开连接，直接发数据包                 |
| 可靠性          | 可靠传输：确认应答、重传、序号、去重、拥塞控制               | 不可靠：不保证到达、不保证顺序、丢包不会重传             |
| 顺序性          | 保证数据按顺序到达                                           | 不保证顺序，数据包可能乱序                               |
| 控制开销        | 头部大（20‑60 字节），控制逻辑复杂，开销大                   | 头部小（8 字节），开销极小                               |
| 速度            | 较慢，有握手、重传、拥塞机制                                 | 速度快，延迟低                                           |
| 流量 / 拥塞控制 | 有流量控制、拥塞控制                                         | 无                                                       |
| 适用场景        | 文件传输、网页 HTTP/HTTPS、SSH、数据库访问，要求数据完整准确 | 直播、视频通话、游戏、DNS 查询，容忍少量丢包，追求低延迟 |

### 通俗理解

- **TCP 如同打电话**：拨号接通（三次握手）→说话→挂断（四次挥手）；对方没听见会重说，保证每句话顺序完整。
- **UDP 如同寄明信片**：直接扔出去，不知道对方收没收到，不管先后，速度快，但可能丢失。
