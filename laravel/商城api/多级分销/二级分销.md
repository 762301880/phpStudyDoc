## 	分销模式

> 核心业务模型（先定规则，不然后面全乱）

###  分销模式（必须先选）

常见三种：

#### ✅ 一级分销（最简单，推荐）

- A 推荐 B
- B 下单 → A 拿佣金

 👉 优点：简单、合规、容易算账
 👉 缺点：裂变弱

------

#### ⚠️ 二级分销（常见）

- A → B → C
- C 下单 → B + A 都有佣金

👉 问题：

- 关系链复杂
- 佣金计算容易错
- 风控难（刷层级）

------

#### ❌ 多级分销（不建议）

- 容易踩法律红线（类似传销）

✔️ 建议：**最多二级，最好一级起步**

## 核心数据结构设计

### 1. 用户表（user）

```sql
CREATE TABLE `user_distribution` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '用户ID',
  `nickname` varchar(100) DEFAULT NULL COMMENT '用户昵称',
  `inviter_id` bigint DEFAULT NULL COMMENT '直接上级id(直推人，关键字段)',
  `path` varchar(500) DEFAULT NULL COMMENT '推荐链路径，例如：1/5/23，从根上级到自身父级',
  `level` int DEFAULT NULL COMMENT '分销层级(相对于根节点的层级)',
  `created_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (`id`),
  KEY `idx_inviter_id` (`inviter_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='分销用户表';

```

`path` 很关键，用来快速查上级链（避免递归）

### 字段说明补充

1. **inviter_id**：只存**直接父级**，唯一直推上线

2. path

   ：存储整条祖先链，用 `/`分隔，方便快速查询所有上级；

   > 例：A (1)→B (5)→C (23)，则 C 的 `path` = `1/5`

3. **level**：层级，A=1，B=2，C=3

### 2. 商品表（product）

```sql
CREATE TABLE `goods` (
```

### 3. 订单表（order）

```sql
CREATE TABLE `order` (

  `status` varchar(20) NOT NULL DEFAULT 'unpaid' COMMENT '订单状态：unpaid待付款、paid已付款、shipped已发货、completed已完成、cancelled已取消',
  `created_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '订单创建时间',
  PRIMARY KEY (`id`),

```

### 4. 分销佣金表（commission）

```sql
CREATE TABLE `commission` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '佣金记录ID',
  `order_id` bigint NOT NULL COMMENT '订单ID',
  `user_id` bigint NOT NULL COMMENT '获得佣金的用户ID(收益人)',
  `from_user_id` bigint NOT NULL COMMENT '下单贡献佣金的用户ID(消费者)',
  `level` tinyint NOT NULL COMMENT '分销层级：1=一级佣金，2=二级佣金',
  `amount` decimal(10,2) NOT NULL DEFAULT 0.00 COMMENT '佣金金额',
  `status` varchar(20) NOT NULL DEFAULT 'pending' COMMENT '状态：pending待结算、confirmed已确认、settled已结算',
  `created_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '记录创建时间',
  PRIMARY KEY (`id`),
  KEY `idx_order_id` (`order_id`),
  KEY `idx_user_id` (`user_id`),
  KEY `idx_from_user_id` (`from_user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='分销佣金明细表';
```

##  佣金计算逻辑

### 下单后触发：

```shell
用户C下单
  ↓
找到C的 邀请人-inviter（B）
  ↓
B拿一级佣金
  ↓
如果有二级 → 找B的 inviter（A）
  ↓
A拿二级佣金
```

### 示例计算：

商品：100元
 一级佣金：10%
 二级佣金：5%

```shell
C买 → 100元

B（一级） → 10元  
A（二级） → 5元
```

正确计算方式（行业通用）

订单金额：100 元

- 一级（B）：
   `100 × 10% = 10 元`
- 二级（A）：
   `100 × 5% = 5 元`

### 总佣金是多少？

> 分销系统默认是：
>  **“每一层都基于订单金额 independently 计算佣金”**

```
总发放佣金 = 10 + 5 = 15 元
```

也就是：

> ✅ **相当于平台拿出 100 的 15% 用来分佣**

但注意一点：

👉 **不是“先给 B 10%，再从 B 里抽 5% 给 A”**

### ⚠️ 注意点：

- 佣金不要“实时到账”
- 必须有状态流转：

   ```php
⚠️ 注意点：
佣金不要“实时到账”
必须有状态流转：
   ```

👉 防止退款导致财务错误

## 关键技术点

### 1.推荐关系绑定（坑点）

用户注册时：

```
?invite_code=xxx
```

👉 必须只绑定一次，不可修改

### 2. 防刷机制

否则分销=送钱

要做：

- 同 IP 限制
- 同设备限制
- 自买自返检测
- 异常订单识别

### 3. 佣金异步计算（重要）

不要在下单接口直接算佣金！

👉 用消息队列（你之前用 RabbitMQ，很适合）

流程：

```
下单成功
  ↓
发送 MQ 消息
  ↓
佣金服务消费
  ↓
写入 commission 表
```

👉 好处：

- 解耦
- 防止接口变慢
- 可重试

### 4. 分销关系查询优化

不要递归查！

用 `path`：

```sql
SELECT * FROM user WHERE id IN (path拆分)
```

### 5. 提现系统（容易出事故）

需要：

- 最低提现金额
- 手续费
- 审核机制
- 打款记录

##  补充

### 分销如何分等级

**如何在 A → B → C 这种推荐关系里，明确谁是一级、谁是二级，并在代码里稳定识别出来**。

**关系定义**

```php
A → B → C
```

含义：

- A 是 B 的邀请人
- B 是 C 的邀请人

那么：

| 角色 | 对 C 来说的层级 |
| ---- | --------------- |
| B    | 一级分销        |
| A    | 二级分销        |

👉 记住一句话：

> **“离下单用户最近的是一级，再往上是二级”**

#### 核心字段设计（决定你怎么判断）

用户表关键字段：

```sql
id           -- 当前用户
inviter_id   -- 直接上级(父节点  如果自己就是父节点null)
path         -- 推荐链，例如：A/B/C
```

**用 A / B / C 举例说明**

假设有这样一条推荐关系：

```
A → B → C
```

意思是：

- A 推荐了 B
- B 推荐了 C

数据会这样存：

用户 A（最顶级，没有上级）

```php
id = A
inviter_id = NULL
path = A
```

用户 B（A 推荐）

```php
id = B
inviter_id = A
path = A/B
```

用户 C（B 推荐）

```php
id = C
inviter_id = B
path = A/B/C
```

**path 是怎么生成的?**

规则很简单：

```php
当前用户    path = 上级用户 path + "/" + 当前用户 id
```

比如：

- B 的 path = A + "/" + B → `A/B`
- C 的 path = A/B + "/" + C → `A/B/C`





#### 代码判断逻辑（重点）

假设：
 当前下单用户 = `C`

✅ 方法1：只用 inviter_id（最简单)

```php
// C
level1 := C.inviter_id   // B

// B
level2 := B.inviter_id   // A
```

👉 判断：

```php
B = 一级
A = 二级
```

✅ 方法2：用 path（推荐，用于复杂场景）

假设：

```
A.id = 1
B.id = 2
C.id = 3

C.path = "1/2"
```

解析：

```
path 最后一个 = 直接上级 = 一级（B）
path 倒数第二个 = 二级（A）
```

#### 佣金分配逻辑（结合层级）

```php
C 下单
 ↓
一级（B）拿佣金
 ↓
二级（A）拿佣金（如果存在）
```

**完整流程**

```php
1. 用户 C 下单
2. 查 C.inviter_id → B
   → 给 B 一级佣金

3. 查 B.inviter_id → A
   → 给 A 二级佣金
```

## 关键限制（必须做）

### ❗ 1. 限制层级深度

```
最多两级，不要无限往上找
```

------

### ❗ 2. inviter_id 必须固定

```
用户一旦绑定上级 → 永远不能改
```

------

### ❗ 3. 防止自己给自己返佣

```
if (A == C) → 不发佣金
```

## 推荐相关(重要)

### A→B→C 那么A还可以推荐C吗(不能)

一个用户只能有 1 个直推上线

C 被 B 锁定 → C 永远不能再被 A 抢成直推。

### A→B→C 后`A还可以推荐D吗`

结论：**完全可以！A 可以推荐 D**

最终团队结构

> A → B → C   A → D

- **D 的直推上级 = A**（D 属于 A 的**一级下级**）
- B、D 两个人是**平级、互不隶属**

收益举例（二级分销，最常用合规模式）

1. B 下单：**A 拿一级佣金**
2. C 下单：B 拿一级佣金，**A 拿二级佣金**
3. D 下单：**A 拿一级佣金**

> ✅ A 可以无限推荐很多个一级下级：B、D、E、F……，没有数量上限。

区分两个容易搞混的概念

1. 一个用户只能有 1 个直推上线
   - C 被 B 锁定 → C 永远不能再被 A 抢成直推。
2. 一个上级可以拥有无数个直推下线
   - A 除了 B 之外，还可以继续拉 D、E、F 等新用户做自己的直接下级。

层级链条对比

```php
A（上级）
├─ B（A的一级）
│   └─ C（A的二级）
└─ D（A的一级）
```

## 绑定等级相关(重要)

B→C(B先推荐了C)

A→B(A还能推荐B吗)

### 现状再理清楚

- B：已注册，`inviter_id = null`（**空白、无上级**），`level=1`
- C：`inviter_id = B`，`level=2`
- B 已经有下线 C 了 现在：A 来邀请 B

这里最关键的分界线：**B 账号早就创建好了，只是缺一个上级**。

### 结论:（最最主流，90% 商用分销）：注册即锁，哪怕 inviter_id 是空，也不能再绑定

> 规则：**只要用户账号已经存在，不管有没有上级，扫码邀请一律无效**。

结果：

- B：`inviter_id=null`，`level=1`，不变
- C：`inviter_id=B`，`level=2`，不变
- A 无法成为 B 的上级

**为什么企业要这么做？**

1. B 已经发展出下级 C，说明 B 已经是推广者；如果后面随便一个人 A 扫一下就能变成 B 的上级，A 凭空享受以后 B、C 带来的佣金，非常不公平。
2. 推广员之间会疯狂 “捡漏”，专门去找那些无上级但是已经有团队的用户，造成大量纠纷投诉。
