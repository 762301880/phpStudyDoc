## 一、按「约束 / 功能」分类（最常用）

### 1. 主键索引 (PRIMARY KEY)

- **定义**：表的主键自动创建的索引，**唯一且非空**，一个表只能有一个。
- **特点**：最快、最核心的索引，数据行物理存储按主键排序（InnoDB）。
- **示例**：`id INT PRIMARY KEY`

### 2. 唯一索引 (UNIQUE)

- **定义**：索引列的值**必须唯一**，允许 NULL（但只能有一个 NULL）。
- **特点**：保证数据唯一性，同时加速查询。
- **示例**：`UNIQUE INDEX idx_phone (phone)`

### 3. 普通索引 (INDEX / KEY)

- **定义**：最基础的索引，**无任何约束**，仅用于加速查询。
- **特点**：最常用，支持重复值、NULL。
- **示例**：`INDEX idx_name (name)`

### 4. 全文索引 (FULLTEXT)

- **定义**：专门用于**文本内容搜索**（如文章、评论关键词检索）。
- **特点**：比 `LIKE %关键词%` 快得多，仅支持 CHAR/VARCHAR/TEXT 类型。
- **示例**：`FULLTEXT INDEX idx_content (content)`

------

## 二、按「字段数量」分类

### 1. 单值索引

- 只包含**一个字段**的索引（上面的主键、唯一、普通索引大多是单值）。

### 2. 联合索引（复合索引）

- **定义**：包含**多个字段**的索引，遵循**最左前缀原则**。
- **核心规则**：查询时必须从索引最左侧字段开始匹配，否则索引失效。
- **示例**：`INDEX idx_user_age_gender (age, gender)`
- **适用**：多条件组合查询（如 `where age=20 and gender=1`）。

------

## 三、按「物理存储」分类（InnoDB 核心）

### 1. 聚簇索引 (Clustered Index)

- **定义**：**主键索引就是聚簇索引**，数据行直接存在索引叶子节点。
- **特点**：查询速度极快，一个表只有一个。
- **注意**：没有主键时，MySQL 会自动用唯一键 / 隐藏字段当聚簇索引。

### 2. 非聚簇索引 (Secondary Index)

- **定义**：除主键外的所有索引（普通、唯一、联合等）。
- **特点**：叶子节点存储**主键值**，查询时需要回表查完整数据。

------

## 四、快速总结（记忆版）

1. **必用**：主键索引（自带，无需手动建）
2. **保唯一**：唯一索引（手机号、邮箱）
3. **加速查询**：普通索引（高频查询字段）
4. **文本搜索**：全文索引（文章、内容）
5. **多条件查询**：联合索引（最左前缀原则）
6. **存储结构**：聚簇索引（主键）+ 非聚簇索引（其他）

### 总结

- 按功能分：**主键、唯一、普通、全文**
- 按字段分：**单值、联合**
- 按存储分：**聚簇、非聚簇**
- 日常开发 90% 场景只用：**主键索引 + 普通索引 + 联合索引**

## 补充:MySQL 索引失效场景（InnoDB，B + 树索引，重点是**最左前缀、隐式转换、范围查询**）

> 前提：默认讲普通 B + 树二级索引，不区分联合索引 / 单索引，执行计划 `explain` 看 `type、key、rows` 判断是否走索引

### 一、联合索引：不满足**最左前缀原则**（高频）

联合索引 `idx(a,b,c)`，索引有序顺序是 `a→b→c`，**必须从最左列开始连续匹配** ✅ 能走：`where a=1` / `where a=1 and b=2` / `where a=1 and b=2 and c=3` 

❌ 失效：

1. 跳过最左列：`where b=2` / `where b=2 and c=3`
2. 中间断列：`where a=1 and c=3`（只能用到 a，c 不走索引）
3. 调换顺序：`where b=2 and a=1` **不会失效！MySQL 优化器会自动调整 where 条件顺序**

> 口诀：**连续、从最左开始；跳过左边，后面全部失效**

### 二、索引列上做**函数、运算、类型转换**（最常踩坑）

**索引列不能参与计算，不能套函数**，否则索引失效，触发全表扫描

```sql
-- 失效：索引字段使用函数
where SUBSTR(name,1,2) = '张'
where DATE(create_time) = '2026-09-29'

-- 失效：运算
where age + 1 = 20

-- 失效：隐式类型转换（经典坑！字符串索引传数字）
-- phone是varchar索引
where phone = 13800138000; -- 索引失效，MySQL把phone转数字，字段做转换
-- 正确写法：where phone = '13800138000'
```

> 本质：**索引存储的是原始值，对列做运算，无法匹配索引树上的值**

### 三、范围查询（> < >= <= between）后面的列，联合索引失效

联合索引 `idx(a,b,c)`

```sql
where a=1 and b>10 and c=20;
```

- a、b 可以走索引；**b 是范围，b 之后的 c 无法使用索引**

规则：**联合索引中，范围条件右边的列，索引失效** 注意：`=` 和 `in` 不算范围，后面字段依旧可以走索引



### 四、like 以通配符 `%` 开头，索引失效

```sql
-- 失效：%在前，无法利用B+树有序特性
where name like '%张三'
where name like '%张%'

-- 可以走索引
where name like '张%'
```

> 补充：`like '%关键词'` 想优化，可用**覆盖索引**或者全文索引

规则：`or` **左右字段必须都有索引**，否则不走索引； ✅ 优化：改成 `union all` 代替 or

### 五、or 连接，一侧没有索引，整个索引失效

```sql
-- id有索引，name无索引 → 整个不走索引
where id=1 or name='张三';
```

规则：`or` **左右字段必须都有索引**，否则不走索引； ✅ 优化：改成 `union all` 代替 or

### 六、MySQL 优化器判断：走索引不如全表扫描，**主动放弃索引**

哪怕索引合法，优化器估算代价后，觉得全表更快，会不走索引：

1. 查询结果集占表数据**很大比例（一般 > 20% 左右，没有固定值）**，比如 `status=1`，大量数据都是 1
2. 小表，数据量很少，全表扫描成本更低，直接放弃索引

> 这是**优化器行为，不是索引本身坏了**，可以用 `force index(索引名)` 强制走索引验证
