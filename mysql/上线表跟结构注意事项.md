## MDL 锁阻塞

> 场景: 线上还有生产或者查询数据的时候我们需要修改字段的某个数据 例如int类型改为varchar

### bug复现

准备一张测试表

```sql
CREATE TABLE `user` (
  `id` BIGINT PRIMARY KEY AUTO_INCREMENT,
  `age` INT COMMENT '要改成varchar的字段',
  `name` VARCHAR(50),
  `create_time` DATETIME
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 随便插一点测试数据，不用1500w，几十条就能复现MDL阻塞
INSERT INTO user(age,name) VALUES(18,'a'),(19,'b'),(20,'c');
```

原理： **一个长事务先打开，持有表的读 MDL 锁不提交 → 后面的 ALTER TABLE 需要排他 MDL 锁，卡住排队 → 后续所有查询、DML 都被 ALTER 堵住排队，整条链路卡死。**

> 这个是线上大表 alter 最经典事故！

打开**3 个 MySQL 客户端会话（窗口 A、B、C）**，按顺序执行，不要乱序！

窗口 A（模拟业务长事务，持有 MDL 读锁，不提交！）

```sql
BEGIN;
-- 随便查这张表，只要事务不commit，就会持有这张表的MDL读锁
SELECT * FROM user WHERE id = 1;
-- ⚠️ 重点：这里先不 commit，挂在这里
```

窗口 B（执行 alter，对应你线上改字段 int→varchar）

```sql
ALTER TABLE user MODIFY COLUMN age VARCHAR(20);

-- 改回int类型
-- ALTER TABLE user MODIFY COLUMN age INT;

```

> **现象：这条 alter 直接卡住，没有返回，处于等待状态！** 原因：alter 需要 **排他 MDL 锁**，但是窗口 A 事务还拿着读 MDL 锁没放，它只能等。

### 窗口 C（模拟持续新增的业务流量，也就是你说的数据还在新增）

```sql
INSERT INTO user(age,name) VALUES(22,'test');
-- 或者 UPDATE / SELECT * FROM user limit 1;
```

**现象：这条 insert/update/select 也卡住！** 复现成功： alter 卡在中间，后面所有读写全部排队阻塞，连接堆积，就是线上 “锁表卡死” 现象。

排查阻塞的 SQL（新开窗口 D 执行）

```sql
-- 查看当前等待MDL锁的会话
SELECT * FROM performance_schema.metadata_locks;

-- 查看线程状态，看到 Waiting for table metadata lock
SHOW PROCESSLIST;
```

###  gh-ost工具解决

> gh-ost 是单二进制文件，**无依赖**，不用装一堆包；重点：**先测试（不加 --execute），确认没问题再上真实执行**

#### 前置检查（必须先做！不满足直接报错）

```sql
-- 1. 查看binlog格式
SHOW VARIABLES LIKE 'binlog_format';
-- 必须是 ROW
SHOW VARIABLES LIKE 'binlog_row_image';
-- 必须是 FULL

-- 如果不是，测试库可以临时改
SET GLOBAL binlog_format=ROW;
SET GLOBAL binlog_row_image=FULL;
```

约束清单：

1. 表**必须有主键 / 非空唯一索引**（你的 user 表 id 主键没问题）
2. **不能有触发器、不能有外键**
3. MySQL ≥5.7
4. 账号权限：`REPLICATION CLIENT,REPLICATION SLAVE,ALTER,CREATE,DROP,SELECT,INSERT,UPDATE,DELETE`
5. 磁盘：需要多出一份表大小空间（影子 ghost 表）

> 加 `--assume-rbr` 参数：已经确认是 ROW 模式，就不需要 SUPER 权限，线上 RDS 非常常用

安装（Linux x86_64）

```bash
# 下载二进制包（找最新release，下面是示例）
wget https://github.com/github/gh-ost/releases/download/v1.1.7/gh-ost-binary-linux-amd64-20241219160321.tar.gz

# 解压
tar zxvf gh-ost-binary-linux-amd64-20241219160321.tar.gz

# 放到全局命令
mv gh-ost /usr/local/bin/
chmod +x /usr/local/bin/gh-ost

# 验证
gh-ost --version
```

**命令模板（场景：user 表 age int → varchar (20)）**

```bash
gh-ost \
--host=127.0.0.1 \
--port=3306 \
--user=root \
--password="你的密码" \
--database=testdb \
--table=user \
--alter="MODIFY COLUMN age VARCHAR(20)" \
--assume-rbr \
--allow-on-master \
--exact-rowcount
```

- `--allow-on-master`：直接在主库跑（测试环境用；有从库的生产一般建议 gh-ost 连从库，自动感知延迟）
- `--exact-rowcount`：精确统计行数，进度条准一点
- `--assume-rbr`：已经是 ROW binlog，跳过检查、不需要 super 权限

跑成功会输出日志，告诉你预估耗时、没有报错，再往下走。

第二步：真实执行（加上 --execute）

> **加上 `--execute` 才是真正开始迁移！**

```bash
gh-ost \
--host=127.0.0.1 \
--port=3306 \
--user=root \
--password="你的密码" \
--database=testdb \
--table=user \
--alter="MODIFY COLUMN age VARCHAR(20)" \
--assume-rbr \
--allow-on-master \
--exact-rowcount \
--execute
```

关键监控 & 限流参数（线上必加，防止 IO 打爆）

```bash
# 复制延迟超过 2000ms 自动限流暂停（默认1500ms）
--max-lag-millis=2000
# 并发拷贝批次，调低降低压力
--chunk-size=1000
# 线程数，不要太大
--concurrent-rowcount
# 负载阈值：运行线程超过80就限流
--max-load=Threads_running=80
```

带上限流完整版示例：

```bash
gh-ost \
--host=127.0.0.1 \
--port=3306 \
--user=root \
--password="xxx" \
--database=testdb \
--table=user \
--alter="MODIFY COLUMN age VARCHAR(20)" \
--assume-rbr \
--allow-on-master \
--exact-rowcount \
--max-lag-millis=2000 \
--chunk-size=1000 \
--max-load=Threads_running=80 \
--execute
```
